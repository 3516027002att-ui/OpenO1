# 模型可操作的 Session / Reasoning Tree

## 背景

Pi 的 Session 设计把会话保存为树结构：每个 entry 都带有稳定标识和父节点关系，因此一个长期任务天然可以分叉、回溯、复制分支并从历史节点重新继续。这与 OpenO1 已经强调的多解法探索、失败路线保留、回溯和计算重分配高度契合。

OpenO1 应进一步把这棵树从“运行时内部数据结构”提升为模型可以直接操作的一等对象。

## 核心决策

OpenO1 内的主模型应拥有对 Session / Reasoning Tree 的一等操作权限。模型可以根据当前推理状态主动决定何时创建、切换、复制、回溯、比较、总结和终止分支，而不需要预先写死固定 workflow。

这里的“可自由操作”指策略层给予模型充分自主权；运行时仍负责结构一致性、权限边界、资源预算和持久化，不允许任意破坏底层状态。

## 建议的一等树操作

模型至少应能够请求以下动作：

- `inspect_tree`：查看当前树、分支状态、节点摘要和未决问题。
- `fork_from(node_id)`：从任意历史节点创建新分支。
- `create_branch(goal)`：围绕新的假设、解法或子问题创建分支。
- `switch_branch(branch_id)`：把当前活动上下文切换到指定分支。
- `checkpoint(label)`：显式保存当前可恢复状态。
- `summarize_branch(branch_id)`：生成用于导航、压缩和后续比较的分支摘要。
- `compare_branches(branch_ids)`：比较多个分支的证据、假设、成本、失败点和结论。
- `merge_branch(source, target)`：把有效结论、证据或状态合并回目标分支；不要求机械拼接完整对话。
- `archive_branch(branch_id, reason)`：将已失败、低价值或暂时搁置的路线归档，但保留可恢复性。
- `resume_from(node_id)`：从历史节点重新构造上下文并继续运行。
- `allocate_compute(branch_id, budget)`：主动把更多模型调用、工具调用或验证预算分配给某条路线。

这些名称只是接口草案，最终实现可以收敛或拆分。

## 树中需要保存的内容

每个节点或分支不应只保存聊天文本，还应关联：

- 稳定 `node_id` / `parent_id` / `branch_id`
- 当前 Goal 与局部子目标
- 模型消息与工具结果
- 推理产物或可公开的结论摘要
- 关键证据与来源
- 假设、未决问题与已发现反例
- 失败原因和被否决路线
- 验证状态
- token、时间、工具调用和其他计算成本
- checkpoint / compaction 元数据
- 创建、切换、归档、合并等生命周期事件

## Compaction 原则

压缩上下文不能破坏树本身。完整历史应继续作为可恢复数据保存；compaction 只决定某次模型调用实际看到什么。

因此：

1. 原始节点和工具结果长期保留或按明确策略归档；
2. summary 是新的派生状态，不覆盖原始历史；
3. 模型可以从任意保留节点重新构造上下文；
4. 不同分支可以采用不同 compaction 策略；
5. branch summary 应记录生成时对应的节点范围和版本，避免摘要漂移后失去来源。

## 与 OpenO1 自主性的关系

这棵树不应只是 UI 提供给用户手工点选。真正重要的是模型能主动把树当作工作记忆和搜索空间来操作，例如：

- 发现两种互斥假设后主动 fork；
- 一条路线验证失败后回到更早节点；
- 给潜力更大的路线增加计算预算；
- 保留失败路线以防后续证据使其重新变得有价值；
- 把多个分支中已验证的局部结论合并回主分支；
- 在结束前主动检查是否还有高价值未探索分支。

这样，长期任务中的“分支、回溯、继续探索”会成为模型的原生动作，而不是 Harness 外部硬编码的 Solver/Critic/Judge 流程。

## Runtime 约束

模型拥有策略自由，但底层状态仍需 fail-fast：

- 禁止形成非法父子关系或循环引用；
- 禁止静默覆盖已有节点；
- merge 必须保留来源和 lineage；
- 删除默认采用可恢复归档，真正物理删除应是高权限动作；
- branch/context 重建失败应立即报错，而不是继续在损坏状态上运行；
- 所有树操作进入事件日志，供 UI、Telemetry、恢复和审计使用。

## UI

Agent 运行状态 UI 应直接可视化这棵树，而不仅显示一条线性的聊天记录。用户至少应能看到：

- 当前活动分支；
- 模型刚刚创建/切换/归档了哪些分支；
- 每条分支的目标、状态、成本和最新有效进展；
- 哪些分支已验证、失败、等待证据或处于暂停状态；
- checkpoint 与 compaction 位置。

用户可以介入操作，但默认情况下模型自己也能完成同样的树操作。

## 与 Pi 的关系

Pi 的树形 Session、fork/tree/clone 和可恢复历史提供了很好的工程参考。OpenO1 可以吸收其数据结构和恢复思路，但进一步把“模型主动操作整棵树”作为自主推理机制的一部分，并与 OpenO1 的计算分配、验证、Capability/Tool 调用和长期任务状态统一起来。
