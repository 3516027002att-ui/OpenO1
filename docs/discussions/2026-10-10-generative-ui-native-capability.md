# OpenO1 原生 Generative UI 能力设计

> 日期：2026-10-10  
> 状态：已确认的能力方向 / 待实现  
> 来源：讨论 [OpenUI](https://github.com/thesysdev/openui) 与 [Open Intelligent UI](https://github.com/thesysdev/open-intelligent-ui) 后的架构决定。

## 核心决策

**OpenO1 应将 Generative UI（生成式交互界面）作为原生能力。**

Agent 可以根据任务和执行状态，自主决定是否生成 UI、生成哪些组件、何时更新现有界面。普通问题可以继续返回文本。UI 不应成为每轮推理的强制步骤，也不应使 OpenO1 绑定固定 Workflow 或固定组件流程。

目标是让 UI 成为 Agent 与用户之间的双向交互 Surface，而不是仅用于美化文本的渲染层。

## 架构边界

建议保持三个职责清晰的层次：

1. **Agent / Harness**：继续负责动态推理、工具调用、任务状态、分支与计算管理、执行授权以及可恢复性。运行时拥有实际执行权限。
2. **结构化输出与事件协议**：承载文本、UI 描述、UI 更新和用户事件。组件实例应有稳定标识，更新应可关联特定实例和状态版本。
3. **UI Renderer / Client Surface**：以受控组件库渲染界面，执行本地交互并回传结构化事件；不直接获得 Harness 的工具执行权限。

OpenUI 可用作组件描述、流式生成和渲染实现的参考。是否直接采用其协议与框架，待原型评估；不把 Open Intelligent UI 旅游演示的具体业务组件硬编码进 OpenO1 的 Runtime。

## 核心能力

- **按需生成**：Agent 自主选择纯文本、结构化 UI 或两者结合；只在需要时提供相关组件定义，避免给所有模型调用注入完整 UI Schema。
- **流式渲染**：增量消费经过校验的组件描述；不完整参数要有容错策略，避免流式输出期间出现错误交互或闪烁。
- **增量更新**：可以修改已有组件的数据、状态和可视表现，而不必每次重新生成整页。
- **双向交互**：按钮、表单、选择器、图表等产生结构化事件，回到 Harness 并按需引起新的推理、工具调用或状态变更。
- **可恢复状态**：UI 事件和必要的展示状态关联任务或消息，并可随会话恢复；避免只靠把 UI 状态写成自然语言来维持一致性。
- **权限隔离**：组件和事件需要 Schema 校验与权限检查。UI 描述不直接执行代码；写文件、访问网络、调用外部工具等副作用仍由 Harness 控制，必要时要求用户确认。

可以将交互协议抽象为：`text`、`ui_spec`、`ui_patch`、`ui_event`。这些是概念性消息类别，不是现阶段固定的 API 命名。

## 首个验证场景：数学推理

围绕 OpenO1 当前的数学推理目标，优先考虑以下用户可见能力：

- 展示问题目标、整体任务进度、已核验的结论、证据与失败提示；
- 展示可公开的候选解法摘要、验证状态及其计算成本；
- 允许用户选择某个候选方向、修改约束、请求继续验证或提出新的问题；
- 在工具验证完成后更新对应结果，无需重复输出整份报告。

**边界：内部 Session / Reasoning Tree、模型内部搜索路径和未公开推理状态默认不直接暴露给用户。** 可交互的是面向用户的结果和任务控制视图。即使 UI 呈现树状关系，也应由独立的可公开数据投影生成，不直接绑定内部推理树结构。这一约束与现有的 [模型可操作的 Session / Reasoning Tree 设计](./2026-08-13-model-operable-session-tree.md) 一致。

## 实施顺序

1. 在输出层预留可选的结构化 UI 消息与 UI 事件接口，不侵入核心推理循环。
2. 评估 OpenUI 的组件定义、流式解析、React 渲染与本地模型兼容性；建立最小可运行原型。
3. 打通用户操作回传、状态持久化、增量更新与权限确认。
4. 面向数学推理补充专用的结果、证据、验证与任务控制组件。
5. 评估额外 Prompt Tokens、首屏时间、渲染失败率、事件一致性与交互完成率，再决定扩展范围。

## 与已有设计的关系

- [DSH 启发的 Harness 架构设计方向](./2026-08-13-dsh-harness-design-notes.md) 已提出 Host / Client 双 Surface 以及 Agent 运行状态的 UI 表达。本设计将“Agent 按需生成交互 UI”进一步明确为正式能力。
- [模型可操作的 Session / Reasoning Tree](./2026-08-13-model-operable-session-tree.md) 规定内部认知树与用户可见界面的隔离，本设计继续遵守。
- 当前仍以数学推理、可恢复状态和运行时执行能力为首要开发重点；Generative UI 是已确认的架构方向，但不要求立即整体引入旅游演示应用。
