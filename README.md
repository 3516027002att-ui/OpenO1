# OpenO1

OpenO1 源自于我最底层的热爱，对AI技术的星辰大海的无限向往，和我对未来技术发展的预判

OpenO1 研究如何利用充足的推理时间、模型调用和计算资源，提高困难问题的求解上限。

系统通过外层运行时组织多轮推理、搜索、代码执行、符号演算、并行探索和外部验证，并维护可恢复的任务状态。运行过程中保留证据、失败路线、未决问题和验证结果，支持长期推进、分支、回溯与重新分配计算。

项目处于早期阶段，当前以数学推理为首个验证场景。

## 当前工作

- 维护可恢复的任务与推理状态
- 管理解法分支、回溯和计算分配
- 接入代码执行、符号计算和领域验证器
- 记录模型调用、工具结果、失败原因和最终证据
- 对比直接回答与长时间运行后的准确率、稳定性和计算开销

## 实现原则

OpenO1 不采用固定的 Solver-Critic-Judge 或多 Agent 流程。系统根据任务状态增加分支、工具、审阅和验证。

运行时负责保存状态、执行动作、管理分支和批准结束。模型负责提出推导、候选结论和下一步动作。关键结论需要验证，失败路线会被保留，额外调用需要产生新的推导、证据、反例或状态变化。

## 规划能力：生成式交互界面（Generative UI）

OpenO1 将生成式交互界面纳入原生能力。Agent 可根据任务与当前状态，自主决定是否生成 UI、选用哪些组件，以及何时更新已有界面。简单任务仍可直接输出文本，不为每轮推理强制附加 UI 开销。

- **输出与渲染分离**：运行时保留推理、工具调用、任务状态与执行权限；界面层消费经过验证的结构化 UI 描述，支持流式渲染和增量更新。
- **双向交互**：图表、表单、按钮和任务视图可接收用户操作。操作以结构化事件返回 Harness，并写入可恢复的任务状态，供后续推理和执行使用。
- **安全边界**：模型生成 UI 不等于取得工具执行权限。组件、参数及事件需经过校验；涉及外部副作用的操作继续由运行时执行并按需确认。
- **按需加载**：根据任务加载相关组件规范，避免向每轮模型调用注入整套 UI 定义。
- **首个场景**：围绕数学推理构建交互式证明树、解法分支、验证结果和计算开销视图，让用户查看状态并选择进一步探索的路线。

实现顺序：先预留结构化输出与交互事件接口；再接入基础组件渲染和流式解析；随后支持增量更新、状态同步和专用推理视图。这项能力不改变当前以数学推理和运行时能力为先的开发重点。

参考：[OpenUI](https://github.com/thesysdev/openui) 与 [Open Intelligent UI](https://github.com/thesysdev/open-intelligent-ui)。借鉴其组件协议和交互机制，不将具体演示应用与 Agent Runtime 绑定。

## 评测

第一阶段评测推理预算与求解质量之间的关系。实验保留模型直接回答的基线，并记录准确率、运行时间、token、工具调用、失败率和运行配置。

目标是把更多计算，真正变成更多智能。
